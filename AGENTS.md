# Project Management Platform — Agent Guide

Procedural **PHP 8.5** project-management console (internal) plus a public, read-only
**client share portal**. MariaDB 10.11 through a PDO singleton, Nginx, vanilla JS/CSS.
No framework, no build step, no npm, no PHPUnit.

## Layout

| Path | Role |
|---|---|
| `index.php` | Front controller — `config.php` → `includes/functions.php` → `includes/Router.php` → `pmpDispatch()`. ~20 lines. |
| `includes/Router.php` | Route table `pmpRouteTable()` + dispatch. **Single source of truth for URLs.** |
| `includes/legacy_redirects.php` | 301s every legacy `.php` URL, **before** any auth logic. |
| `includes/functions.php` | 42 helpers: `e()`, CSRF, date parsing, task rollups, rate limits, share codes. |
| `includes/header.php` / `footer.php` | Internal shell (`.app-shell` / `.sidebar` / `.topbar`) + flash messages. |
| `includes/landing.php` | Public landing page body (share-code form). |
| `includes/security_headers.php` | CSP + security headers — separate internal and client variants. |
| `includes/task_edit_auth.php` | IDOR guards for task assignment. |
| `includes/slug.php` | Slug generation / lookup. |
| `includes/Database.php` | PDO singleton wrapper. |
| `*.php` (repo root) | **Routing targets, not standalone pages.** The router `require`s them by filename. |
| `ajax/*.php` | 6 JSON endpoints. |
| `client/` | Public portal — own `<head>`, own CSS/JS, `client/lang.php` (EN + 中文). |
| `database/` | `schema.sql`, `migrations/`, `*_test.php`. |
| `assets/` | `css/v2-tokens.css`, `css/style.css`, `css/v2-components.css`, `css/pages/*.css` (13 files), `js/script.js`. |

`config.php` is **gitignored** — it is hand-maintained per deployment (and regenerated by
`install.php`). `config.template.php` is the tracked twin: it must declare the **same 21
constants** (only the values differ — the template carries placeholders like
`your_db_password`). Add or remove a constant in one, add or remove it in the other.

## Runtime and installation targets

Two facts that constrain almost every change in this repo.

### PHP 8.5 is the floor, not just the dev image

The `Dockerfile` pins `FROM php:8.5-fpm-alpine` — that is the **source of truth** for the
runtime version. PHP 8.5 is the minimum supported version (8.3/8.4 carry unpatched
vulnerabilities), so:

- `composer.json` must require `"php": ">=8.5"`.
- `install.php` must advertise **PHP 8.5 or higher** in its requirements panel.
- `README.md`'s tech-stack table must say **PHP 8.5**.
- Writing code that *requires* 8.4+/8.5-only syntax is fine — the floor is 8.5.

Do not silently regress the floor to `>=8.3` in any one of those four places; they are a
set.

### Docker Compose is DEVELOPMENT ONLY

`docker-compose.yml` is a developer convenience. **The application must install and run
without Docker** — that is a hard requirement, not a nice-to-have. Production runs on
plain LAMP / shared hosting (Hostinger / cPanel Apache, `public_html`).

The rules that follow from this:

- **The app reads configuration from `config.php` and nothing else.** No `getenv()`,
  no `$_ENV`, no `.env` parsing in application code. `docker/entrypoint.sh` translates
  environment variables into `config.php` *before* the app starts — that translation is
  the Docker-specific part, and it lives in `docker/`, not in `includes/`.
- **Never add a code path that only works under Docker.** If a feature needs a setting,
  add a `config.php` constant.
- There are **two** config-generation paths, and both must stay in sync on the constant
  set (21):

  | Path | Used for | Writes `config.php`? |
  |---|---|---|
  | `install.php` (4-step web wizard) | **Universal** — the non-Docker install path | Yes, all 21 constants |
  | `docker/entrypoint.sh` | Dev convenience only | Yes — must emit the same 21 constants |

- The **web server differs by target** and both must route to the front controller the
  same way:

  | Target | Server | Front-controller rewrite |
  |---|---|---|
  | Dev (Docker) | Nginx | `docker/nginx.conf` — `try_files $uri $uri/ /index.php?$query_string` |
  | Prod (shared hosting) | Apache | `.htaccess` — `RewriteRule ^(.*)$ index.php [QSA,L]` |

  A new route must work under **both**. If you add a rewrite or a deny rule, add it in
  `docker/nginx.conf` **and** in `.htaccess`.

  `database/apache_nginx_parity_test.php` extracts the deny patterns from both
  files and fails if the two servers disagree. Run it after touching either config.

- **Apache 2.4 constraints** — these have each cost a full outage:

  | Constraint | Consequence if violated |
  |---|---|
  | `<DirectoryMatch>` is **server-config context only** | Apache rejects the whole `.htaccess` → **500 on every request**. Express directory denies as `RewriteRule … [R=404,L]`. |
  | `mod_rewrite` must be **enabled** | `RewriteEngine On` → `Invalid command` → **500 on every request**. The official `php:apache` image does not enable it (`a2enmod rewrite`). |
  | `<FilesMatch>` authz runs **before** the rewrite (fixup) phase | An unconditional `<FilesMatch>` turns every intended 404 into a **403**. Keep them inside `<IfModule !mod_rewrite.c>`. |

  Apache answers **403** for `/.htaccess` (its own core protection) where nginx
  answers 404 — the file is not served either way.
- Migrations are **not** auto-run on either path — they are applied by hand (or by
  `install.php` on a fresh install).
- `database/schema.sql` is the single source of truth for the schema on both paths. The
  `db` service mounts it as `/docker-entrypoint-initdb.d/01-schema.sql`, which only fires
  on a **fresh** volume — a dev who edits `schema.sql` must `docker compose down -v` to
  re-seed, or apply a migration instead.

## URL contract

- The internal console lives at the **domain root**: `/dashboard`, `/projects`, `/tasks`,
  `/contacts`, `/profile`, `/login`, `/register`, `/logout`, `/forgot-password`,
  `/reset-password`.
- Detail URLs use **numeric IDs**: `/projects/1692`, `/tasks/935`, `/contacts/249`. Slugs are
  **immutable** (assigned once on insert, never regenerated on rename), but they are no longer
  the public URL — so slug routes exist **only to 301** to the ID form.
- Deletes are **POST-only**: `/projects/<id>/delete`, `/tasks/<id>/delete`, `/contacts/<id>/delete`.
- The public landing page is `/` (accepts `?code=`). The client portal is
  `/client/dashboard.php?code=<SHARE-CODE>` — **not** in the router table.
- Legacy `/foo.php` → 301 → `/foo`. Never link to a `.php` URL.
- `?code=` is a share code, **never** a slug.

## Auth & authorization

There is **no role system**. Access control is per-project ownership:
`projects.responsible_person_id → users.id`. A user sees only the projects they own.

- `requireLogin()` is the only gate — call it **before** any DB work.
- Ownership is enforced **in the SQL**, by joining `projects`:

  ````php
  $row = $db->fetchOne(
      "SELECT t.* FROM tasks t JOIN projects p ON t.project_id = p.id
       WHERE t.id = ? AND p.responsible_person_id = ?", [$id, $user_id]);
  if (!$row) { redirect('/tasks'); }
  ````

- `redirect()` rejects non-absolute URLs (a relative path resolves against the current
  directory and 404s).
- Logged-out deep links land on `/login?redirect=<urlencoded>`; the target is validated by
  `is_safe_return_path()`.

## Commands

`php` is **not on the host PATH** — always run inside the container. These commands are
**dev-only conveniences**; none of them are a prerequisite for a non-Docker install.

```bash
# One regression test
docker exec project-management-platform-app-1 php /var/www/html/database/<test>.php

# Whole suite — the exit code is the signal, not the output
pass=0; fail=0; for t in $(ls database/*_test.php client/*_test.php); do
  if docker exec project-management-platform-app-1 php /var/www/html/$t >/dev/null 2>&1; then pass=$((pass+1));
  else fail=$((fail+1)); echo "FAIL $t"; fi; done
echo "=== $pass PASS / $fail FAIL ==="

# Lint — always, on every file you touch
docker exec project-management-platform-app-1 php -l /var/www/html/<file>.php

# Apply a migration (migrations are NOT auto-run)
set -a; source .env; set +a
docker compose exec -T db mariadb -u"$DB_USER" -p"$DB_PASSWORD" "$DB_NAME" < database/migrations/<file>.sql

# Services: db, app, web (nginx, :80). The mockup is profile-gated (:8080)
docker compose up -d
docker compose up -d mockup
```

### Installing without Docker (the production path)

This is the **supported** install. Docker is not involved at any point.

1. Copy the tree to the web root (`public_html` on shared hosting).
2. Point the domain's document root at it and ensure the front-controller rewrite is
   active — `.htaccess` already contains it for Apache. For Nginx, copy the equivalent
   rules from `docker/nginx.conf`.
3. Make the application directory **writable** — `install.php` writes `config.php` into it.
4. Create an empty database and a database user.
5. Browse to `/install.php` and run the wizard: it validates the connection, creates the
   schema from `database/schema.sql`, collects the SMTP settings, and writes `config.php`.
6. Delete or lock `install.php` afterwards.
7. Apply any migrations newer than the schema the wizard created.

Run `php /path/to/_diag.php` from the shell on the deployed box for the read-only sanity
probe — it checks the PHP version, the 5 pinned md5sums, the security headers, and the
landing page.

## Hard rules

These are the traps that have actually cost time in this repo.

### A test passes on exit code, not on output

Success markers are inconsistent (`ALL ASSERTIONS PASSED`, `All checks passed.`, free-form
prose, or nothing). Detect success by **exit code 0**. Never grep for the literal `Failed` —
`Failed: 0` is an informational line. Never treat "no output" as a pass.

### `Database::execute()` returns bool, not a row count

````php
$db->execute($sql, $params);
$id = (int)$db->lastInsertId();        // correct
$id = (int)$db->execute($sql, $params); // BUG — always 1
````

`EMULATE_PREPARES` is **false** → native prepares → **no multi-statement**. One statement
per call.

### PHP tokenizer traps

- A literal `?>` inside a `//` comment **still closes PHP mode** — the rest of the file
  becomes raw HTML.
- A literal `<?php` inside a `//` comment **still opens a script block**.
- A `/* … */` comment containing `*/` terminates early → `php -l` reports `Unmatched '}'`.
- Write "PHP close tag" / "PHP open tag" in prose instead. **Always `php -l` every changed file.**

### Output escaping

`e()` (`htmlspecialchars(..., ENT_QUOTES, 'UTF-8')`) on **every** dynamic value in HTML.
`sanitize()` is for *input* on login only — it is not a substitute for `e()`.

### CSRF

Validate the token **before** reading any input, and put the hidden input in **every** form:

````php
if (!validateCsrfToken($_POST['csrf_token'] ?? null)) { $errors[] = '…'; } else { /* all work here */ }
````

````html
<input type="hidden" name="csrf_token" value="<?= e(getCsrfToken()) ?>">
````

### Sessions

`startSession()` must be the **first** call in a page — it opens `ob_start()`, because
PHP-FPM here runs `output_buffering=0`. Any byte emitted before it breaks `header()`, and the
CSP silently disappears. In a CLI render proxy, do session setup **first**, then `ob_start()`,
then any debug output, then `require` the target.

### Dates

Use the strict helpers (`parseFormDate()`, `parseCalendarDate()`, `parseUtcDateTime()`).
**`DateTime::createFromFormat()` is deliberately not used** — it returns a `DateTime` with
warnings (not `false`) for impossible dates like `2026-02-31`, so `if (!$date)` never fires.
Completion dates are **day precision** (`type="date"`), never `datetime-local`.

### Never `shell_exec('mariadb …')`

The app container ships **no** MySQL/MariaDB client — the call is a silent no-op. Use
`Database::execute()`. `shell_exec('php …')` **is** allowed (php is on PATH in the container),
but the proxy file must be cleaned up with `register_shutdown_function()` and the target must
be `realpath()`'d.

## Frontend

- **No inline `<style>` or `<script>` blocks.** Page CSS → `assets/css/pages/<page>.css`;
  shared behaviour → `assets/js/script.js`.
- **CSS layer order is load-bearing**: `v2-tokens.css` → `style.css` → `v2-components.css`
  → `pages/<name>.css`. Legacy first so v2 wins at equal specificity. `v2-components.css` is
  linked by `includes/header.php` **only when `$use_v2_shell` is truthy** — pages with their
  own `<head>` (the client portal, `includes/landing.php`) must link it explicitly.
- **Asset paths are root-absolute** (`/assets/css/…`) via `asset_url()` for cache-busting. One
  exception: the landing page's `<script src="/assets/js/share-code-format.js" defer></script>`
  must stay the **literal unversioned** path — it is test-pinned.
- **Dark mode is a designed feature**, not a bug: `prefers-color-scheme: dark` redefines the
  whole `--gray-*` scale.
- v2 status modifiers use a **double** hyphen: `.status--on_hold`, not `.status-on_hold`.
- Some classes exist **only** as regression-test guards — do not rename them away:
  `.task-reason-card`, `.derived-pill`, `.inherit-indicator`, `.reason-chip--delay`,
  `.reason-chip--on-hold`.
- Client-portal JS is hand-written **ES5** (`var` only — no arrow functions, no template
  literals) to match `assets/js/script.js`.
- The server is the single source of truth for the "delayed" predicate: `task_edit.php`
  publishes `data-reason-show="0|1"` and the JS reads it. Do not re-derive the date rule in
  JS, and do not weaken the server-side validation.

## Schema changes

1. Add `database/migrations/YYYYMMDD_short_name.sql` with an `information_schema` guard —
   idempotent, no `START TRANSACTION`, with the run command documented in the header.
2. Mirror the column in `database/schema.sql` (fresh installs read that file).
3. Add a DB-backed regression test that seeds with a random marker and cleans up in
   `try { } finally { }`.
4. Update column-specific tests only if you are renaming or dropping.

Migrations are **not** auto-run. `schema.sql` is mounted at
`/docker-entrypoint-initdb.d/01-schema.sql`, so it only applies to a **fresh** volume
(`docker compose down -v` re-seeds).

## Release

`APP_VERSION` must stay in lock-step across **five source sites**: `config.php`,
`config.template.php`, `install.php` (`$current_version`), `database/about_popup_test.php`
(the `define('APP_VERSION', …)` drift-guard fixture), and `database/install_wizard_test.php`
(the expected-constant array). Plus two docs: the `RELEASE.md` top entry and the `README.md`
banner. `database/about_popup_test.php` fails the build when the source literal drifts.

`_diag.php` also hard-codes md5sums for `config.php`, `client/dashboard.php`,
`client/lang.php`, `includes/header.php`, and `includes/functions.php` — these 5 pins **MUST
be re-bumped at every release**, in the same commit as the source change
(`md5sum config.php client/dashboard.php client/lang.php includes/header.php
includes/functions.php` → the `$expected_md5` array). `database/probe_diag_test.php` fails if
a `FILL_IN_AT_RELEASE_TIME` placeholder is left behind.

The canonical checklist is [docs/RELEASE_PROCESS.md](docs/RELEASE_PROCESS.md).
