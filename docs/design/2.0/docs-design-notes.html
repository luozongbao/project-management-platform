v2.0 Design & Implementation Notes

How the mockup maps onto the production PHP application: token transplant, component contract, migration order, accessibility rules and the i18n plan.

1. Layer model

The v1.8.0 frontend is a single assets/css/style.css (984 lines, Bootstrap-4-era hardcoded colours, per-page inline CSS duplicated across files) plus a top navbar shell in includes/header.php.

v2.0 replaces this with three layers:

LayerFileResponsibility
Tokensassets/css/v2-tokens.cssAll colour, type, spacing, radius, shadow, z-index and layout variables. Zero selectors beyond :root.
Base + componentsassets/css/style.css (rewritten)Reset, typography, layout primitives and every component class used by the mockup.
Page CSSassets/css/pages/*.cssOnly genuinely page-specific rules (e.g. client portal grid). Everything else is a component class.

Rule of thumb: if a rule appears on more than one screen it belongs in the component layer.

2. Shell migration

The current shell is a top navbar. v2.0 moves to a fixed left sidebar + topbar layout:

v1.8.0 elementv2.0 elementNote
.navbar / .nav-brand.sidebar__brandBrand icon + APP_NAME + version.
.nav-menu + .nav-link.sidebar__nav + .sidebar__linkSame four destinations, plus optional count badge.
.nav-dropdown (user).dropdown in .topbar__actionsProfile + Logout unchanged.
.app-about details panelAbout <details> in the topbarVersion, "Built by", release summary.
.main-content.with-nav.content inside .app-mainPadding is now token-driven.
floating About (logged-out)Retained on public pagesMust stay reachable without JS.

3. Implementation order

  1. Land v2-tokens.css and the reset/base layer. Nothing else changes visually yet.
  2. Land the component layer (buttons, cards, forms, tables, badges, statuses, reason chips).
  3. Replace the shell in includes/header.php / includes/footer.php with the sidebar + topbar.
  4. Convert pages in order of risk: dashboard.php → projects.php → tasks.php → contacts.php → detail pages → forms → auth pages → client/dashboard.php.
  5. Run the existing database/*_test.php suite after each page conversion — those tests assert on HTML structure, so they will catch markup regressions.
  6. Delete the per-page inline <style> blocks as each page is converted.
  7. Only then remove the v1.8.0 rules from style.css.

5. Internationalisation plan

The internal app is currently English-only; the client portal is bilingual (ENG / 中文) via client/lang.php. v2.0 keeps the client portal bilingual and prepares the internal app for it without forcing the migration.

  • Every client-facing string in the mockup carries data-i18n="English|中文" as the interim mechanism.
  • Production keeps the existing t('dash.*') key namespace — no new key scheme is introduced.
  • The mockup adds keys for the v1.8.0 reason strings: dash.delay_reason, dash.on_hold_reason, dash.delayed_count, dash.on_hold_count.
  • Language choice persists in a 1-year cookie (client_set_lang_cookie) — the mockup uses localStorage for demo only.

7. Dark mode

Dark mode is provided through prefers-color-scheme and token overrides only — no component rule is duplicated. The v2.0 mockup ships the light theme; the token overrides for dark are specified in v2-tokens.css §10 and are opt-in for the production implementation.

Status pairs must be re-checked against the dark surfaces — the light-theme pairs are guaranteed AA, the dark pairs are the dev's responsibility to verify before shipping.

8. Red line

v2.0 is a restyle, never a refactor of behaviour
No route, field, action, permission, CSRF token, rate limit, share-code flow, validation rule or email notification may be removed or weakened by the redesign.

The authoritative route-by-route and field-by-field mapping is docs/issues/issue-035.md §9 (Traceability Matrix). Any screen change that cannot be traced to that matrix is out of scope.
